What are we building, and does the plan hold up?

QueryGuard, the safety gate for AI-written SQL · Mahd & Arwa · Prepared by Mahd, September 12, 2026 · For Arwa's review before submission

Summary The requirement document is written and the system it describes already exists and works. The shape: a user asks a question, an AI drafts a database query, and a deterministic gate checks that query against nine safety rules before it runs. Dangerous queries are blocked with an explanation, private columns like SSNs are removed from answers, and every decision is logged in a tamper-evident style record anyone can inspect afterward. The measured results on our 64-case test set are strong: every attack stopped, zero false alarms, checks taking well under a millisecond. The honest thin spots: the live AI mode is not built yet (the demo runs on a deterministic stand-in, by design), and one advanced rule (does the query match what the user actually asked) is marked stretch and can be dropped without hurting the demo.

1 · The product in one path

Every question follows the same five steps, and that path is the whole product:

StepWhat happensWhy it matters
1. IntakeThe question enters through one door, so every request is recorded the same wayNo side doors means no unlogged decisions
2. DraftThe AI writes the SQL query that would answer the questionThis is the powerful, risky part: the AI's output is never trusted directly
3. The gateNine safety rules run on the parsed query. PASS, BLOCK, or MASK (private columns removed)This is the project. Every rule is a numbered requirement with its own test
4. ExecuteOnly passed queries touch the database, on a read-only connectionEven if a rule were bypassed, the database physically cannot be changed
5. The logEvery decision is written down before the user sees anythingThe audit page lets anyone verify what ran and why

2 · The nine rules, in plain language

RuleWhat it stops
No destructive statementsQueries that change or delete data. The database is read-only, full stop
One query at a timeStacking a second command onto a question ("...also drop that table")
No hidden write commandsWrite commands disguised with comment tricks, caught by cleaning the query before judging it
Only allowed tablesAnything outside the published clinic tables
Private columns stay privateSSNs and billing status never appear in answers, including sneaky routes: grouping, ordering, or combined lists that leak them indirectly
No system-table snoopingQueries that map the database's own structure
No execution tricksCommands that run code, attach files, or flip settings
Huge answers get a hintUnbounded reads still run, with a suggestion to add a limit
Answer must match the question (stretch)The query must actually do what the question asked. Marked droppable without hurting the demo
